# Releases

Timeline uses Changesets to record release intent independently of its scoped commit titles. Every pull request must add either a release note with `bun changeset` or an empty decision with `bun changeset --empty`. Renovate's dependency update pull requests, from `renovate/` branches, are the exception: Renovate can't run `bun changeset`, so CI skips the changeset check for them and dependency updates don't appear in the changelog.

Choose `patch` for compatible fixes and performance improvements, `minor` for compatible features, and `major` for incompatible changes. Changelog summaries should describe the effect for somebody using Timeline rather than the implementation.

The Release workflow runs on every push to `main` and does one of three things, decided by Changesets:

- **Pending changesets**: it creates or updates a release pull request, which applies them to propose the next product version, update `CHANGELOG.md`, and synchronize the macOS bundle version. Its title includes the proposed version so you can identify the release before opening it. Review that PR to see the release notes before publishing.
- **No changesets and the current version is untagged**, which is the push that merges the version PR: it runs static, backend, and frontend checks alongside sharded browser tests, including the full chart sweeps and Linux visual snapshots. Once every check passes, `bun changeset git-tag` names the `v<version>` tag. The workflow creates that tag at the tested commit and creates a draft GitHub release from it with the matching changelog entry. If the tag cannot be created at that commit, the run fails before any release is created. Packaging publishes the draft only after its macOS assets are attached.
- **Otherwise**: nothing.

**Merging the version PR is the release approval.** No separate approval, dispatch, or manual tagging is needed. The workflow needs **Actions → General → Allow GitHub Actions to create and approve pull requests** enabled, and existing branch review/check requirements still apply. It never pushes commits directly to `main`.

Timeline remains a private package. `privatePackages.tag` lets Changesets tag it, and the publish step runs the tag-only command instead of npm publishing. Changesets owns tag naming; the workflow creates the tag and the release itself, so a release can only be published at the commit that was tested.

If the publish run fails before the tag is pushed, rerun the Release run for the version PR's merge push; a rerun uses that same commit. If the tag was pushed but release creation failed, first check `gh release view <tag> --json isDraft` with authenticated access: creation may have succeeded despite a lost response. If a draft exists, dispatch **macOS DMG** on `main` with that tag and its full commit SHA; if already published, inspect its assets instead of recreating it. Only after confirming no release exists (rather than a permission or network failure), save a draft from the existing tag in GitHub's Releases UI with the matching `CHANGELOG.md` entry, mark prerelease tags as prereleases, and dispatch packaging. Never create a second release for the same tag; packaging refuses ambiguous matches. Rerunning the whole Release workflow skips existing tags; it does not recreate the draft or resume packaging. If tests fail for a reason a rerun cannot fix, land the fix with a changeset and merge the next version PR; the skipped version keeps its changelog entry but never gets a tag. Never move a published tag.

The root `package.json` is the source of truth for the product version. `tools/timeline-app/Info.plist` is a checked mirror maintained by `bun run version:sync`; `bun run version:check` rejects drift. The web package is private and has no independent version.

`CFBundleVersion` is a separate numeric build identifier, added to the built app rather than committed in `Info.plist`. Local app and service builds default to `scripts/print-build-number.sh`, the same script packaging CI uses for `TIMELINE_BUILD_NUMBER`. The override remains available. Retries at the same commit use the same number and subsequent releases on `main` advance it. Use a full-history checkout so the reachable commit count is accurate.

An installed source build is offered releases with a higher build number. A branch ahead of `main` can out-number the next release, delaying update offers until a release surpasses that branch build.

After the draft is created, the macOS DMG workflow builds the tagged source on an Apple Silicon runner, signs and notarizes it, then attaches the DMG, checksum, and update feed. Only then does it publish the release, marking a stable tag as latest unless a newer stable version is already published, and keeping prereleases out of latest. A packaging failure leaves a draft; rerun the failed packaging job or dispatch **macOS DMG** to complete and publish it. See [macOS distribution](macos-distribution.md#failed-packaging-and-retries) for signing setup and recovery, including partial uploads.

The Git tag exists throughout packaging, independently of the draft. Saving a draft does not create a missing tag; the workflow explicitly creates the remote tag first and uses `--verify-tag`. Git consumers and Changesets therefore see the new tag immediately, even though release consumers still see the previous published release.

## Edge builds

Nothing builds automatically until the repository variable `EDGE_BUILDS_ENABLED` is `true` (a manual run with `dry_run=false` builds regardless); `NIGHTLY_ENABLED` is no longer used. Then, after every push to `main` whose Trusted CI run finishes, the Edge build workflow builds the newest green `main` commit that is newer than both the build the edge release offers and the latest stable release. A stable release commit is skipped, because the release workflow builds it. One build runs at a time: GitHub keeps at most one run waiting, a newer run replaces it, and a newer push does not cancel the build in progress. A run that starts builds whatever is newest then, so a burst of merges usually produces two builds rather than one per merge.

A build is signed and notarized by the same macOS DMG workflow as stable releases, from the commit itself, with the version `<next patch>-edge.<build number>` (for example `0.21.1-edge.1347`). The version exists only in the build; edge builds consume no changesets, create no tags and never change `package.json`. Everything lives in one rolling prerelease, tagged `nightly` because Macs follow its download URL: the update feed `appcast.xml` and the DMGs and checksums of the newest 5 builds. Sparkle generates, applies and signs a direct patch from each of the four other retained edge builds and the latest stable build when possible. Publishing checks the DMG and patch enclosures, uploads their files before switching the feed, then removes superseded patches and expired DMGs. A job beside the macOS build writes notes from the changesets at the built commit to the run summary, and once the feed has moved, publishing puts them in the `nightly` release's description: what is new since the build the feed offered before, then everything else unreleased since the last stable release, leaving out empty changesets (`scripts/ci/edge_notes.py`). Nothing changes a changeset. If the notes cannot be built they read "Notes unavailable.", and the build still ships; a failed description update only marks that step. A dry run prints the notes it would publish. A Mac with a matching build downloads its patch. Other Macs, including those where patching fails, download the full DMG. A Mac that fetched an older feed can still find its DMG removed by a later build, and replacing `appcast.xml` briefly leaves no feed; either way the Mac's check fails and it tries again at its next one. Builds older than the newest 5 are not kept anywhere; to go back further, install a stable DMG. Never delete the `nightly` release or its tag.

To stop automatic builds, set `EDGE_BUILDS_ENABLED` to anything else (`gh variable set EDGE_BUILDS_ENABLED --body false`) or disable the workflow (`gh workflow disable edge.yml`). A build already running finishes.

A manual run is a dry run unless you turn that off: `gh workflow run edge.yml --ref main` prints the commit, version and the DMGs a build would remove, without signing, uploading or deleting anything, and never displaces a waiting build. `gh workflow run edge.yml --ref main -f dry_run=false` builds now.

If a run fails:

- **Before or during the macOS build:** nothing Macs see has changed. The next green push builds again; to build this commit now, re-run the failed jobs.
- **Uploading the DMG or the feed:** uploads retry three times. If they still fail, the release may hold the new DMG without a feed pointing at it, or have no `appcast.xml` at all, and Macs following it get a failed check. Re-run the failed jobs: publishing restores the feed from the run's own build. It refuses only if a newer build's DMG is already there, in which case re-run that build's run instead. A later run also restores the feed when it publishes. For manual recovery, first verify and upload the exact DMG, checksum and every delta referenced by the archived feed. Only then restore the feed: `gh run download <run-id> -n edge-<version> -D out && gh release upload nightly out/appcast.xml --clobber`.
- **Removing old DMGs:** the feed has already moved, so Macs are unaffected. The step refuses the whole removal when the release holds anything it does not recognise, such as a file that is not `appcast.xml` or an edge DMG with its checksum or a recognised Sparkle patch, a DMG without a checksum, or a newest DMG other than the build the feed offers. Remove the stray file with `gh release delete-asset nightly <name> --yes`, then re-run the failed jobs; publishing sees that the feed already offers the build and only removes. A run removes at most five expired DMG/checksum pairs and 25 superseded patches. If more accumulate, inspect the current feed and remove obsolete patches before their target DMGs, then rerun cleanup.

To follow edge builds on a Mac, point Sparkle at the edge feed, then quit and reopen Timeline:

```sh
defaults write com.incognitojam.timeline SUFeedURL https://github.com/incognitojam/timeline/releases/download/nightly/appcast.xml
```

Sparkle reads `SUFeedURL` from user defaults before `Info.plist`, and logs a warning that it can ignore. To go back, run `defaults delete com.incognitojam.timeline SUFeedURL` and reopen Timeline. Sparkle never downgrades, so the Mac keeps its edge build until a stable release with a higher build number appears.

Edge builds check for updates every hour, Sparkle's shortest interval, instead of Sparkle's daily default, which stable builds keep; a Mac that is awake and installs what it is offered then usually has a patch for the newest build. An edge build from before this change checks daily: run `defaults write com.incognitojam.timeline SUScheduledCheckInterval -int 3600` to make it check hourly, and `defaults delete com.incognitojam.timeline SUScheduledCheckInterval` to undo it, which you also need when going back to stable because user defaults override the build's setting. Hourly checks can show an update prompt every hour on a busy day. To install without one, tick **Automatically download and install updates in the future** in the update window, or run `defaults write com.incognitojam.timeline SUAutomaticallyUpdate -bool true`: Timeline then downloads each update in the background and, as soon as it is ready, quits, holds the service, installs and relaunches, so on a busy day the service restarts up to once an hour, possibly mid-sync. That setting also outlasts a move back to stable; undo it with `defaults delete com.incognitojam.timeline SUAutomaticallyUpdate`.

## Release information in Settings

Settings displays the latest stable GitHub release and its notes. Packaged installations compare their product version with that release; source builds show release information without claiming to be current. Drafts and prereleases are excluded: during packaging or after a failure, Settings keeps showing the previous stable release and its download link. The new stable release and DMG appear together after publication and the next uncached check. Before the first stable publication, the check reports the release as unavailable. Checking in the browser does not install an update on the host.

The service makes the GitHub request and shares checks across browsers for one minute. Private repositories use `GITHUB_TOKEN` from the service environment, or the token already configured in `~/.config/timeline/github.json`. The token needs permission to read repository releases and never reaches the browser. Set `TIMELINE_RELEASE_REPOSITORY` to `owner/name` to use a different release repository. Public repositories can be checked without credentials. Permission, network, and metadata failures appear as failed checks rather than an “up to date” result.

The Sparkle feed at `releases/latest/download/appcast.xml` and other `releases/latest` download URLs also stay on the previous published stable release until publication. This does not add an appcast to older releases that lack one. Build and packaging scripts use explicit tags or checkout history, not latest-release discovery.
